Current truth and planned direction

Stabilize before expanding

The application is appropriate for a trusted-LAN demonstration. Reliability and protocol validation should be completed before resume, catalog search, or multi-source scheduling adds more states.

Roadmap with dependencies

Phase 1 — reliable current transfer

Next Fix R-001 through R-007, add protocol/unit tests and two-peer localhost integration tests, improve visible errors, timeouts, cancellation, and shutdown. This is the foundation for every later phase.

Phase 2 — resumable chunks

Persist a .part.meta record containing file hash/size, chunk size/count, and received bitmap. Add resume negotiation and downloader requests. Validate that metadata and temporary content belong together before reuse.

Phase 3 — shared-file catalogue

Peers index chosen shared folders and advertise stable content IDs plus names and sizes. The tracker evolves from peer directory to metadata catalogue. Search results must distinguish content from individual source peers.

Phase 4 — true multi-source download

A downloader-owned session requests selected indices from several sources, schedules missing work, deduplicates completion, retries from another source, and verifies one final content ID. Random-access writing is reusable; the current sender-driven loop is not sufficient.

Phase 5 — demonstration polish

Add speed/ETA, source count, chunk visualization, durable teaching logs, and a scenario where one source stops while the downloader continues elsewhere. These claims should be demonstrated only after the multi-source scheduler exists.

Security boundary

The current trust model is “known participants on a controlled private network.” SHA-256 detects inconsistency with the sender’s claim but does not establish trusted identity. Do not expose tracker or peer ports to an untrusted network as if they were production services.

Revisit architecture when

  • Peers operate behind NAT or across the public internet.
  • Users require authenticated identity, authorization, private transfers, or audit history.
  • The tracker must survive restart or scale beyond one in-memory process.
  • Multi-source scheduling or large concurrency makes one thread per session unsuitable.
  • Cross-language clients require a deliberately portable string encoding and version negotiation.

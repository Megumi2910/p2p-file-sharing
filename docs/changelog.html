2026-09-06 — True multi-source download with dynamic chunk scheduling and peer failover (Phase 4)

Feature / Multi-Source

  • Why: Allow downloaders to fetch files concurrently from multiple providing peers in parallel, maximizing download throughput and guaranteeing transfer completion even when individual peers disconnect or fail.
  • Behavior: Implemented CHUNK_REQUEST (code 108) pull protocol message. Provider peers serve chunk requests over persistent TCP connections. Implemented ChunkScheduler managing missing chunks, preventing duplicate in-flight requests, and reassigning chunks upon peer failure. Implemented MultiSourceDownloader coordinating parallel worker connections, synchronized random-access writes, atomic .part.meta updates, whole-file verification, and publication. Integrated into TransferManager.downloadMultiSource and PeerRuntime.downloadFile.
  • Compatibility/configuration: Fully compatible with sequential v1 transfers and resume staging. Bounded concurrency respects transfer.max.concurrent.
  • Verification: mvn -B -ntp clean verify passes 77 unit and integration tests with 0 failures across common, tracker-server, and peer-app modules, including ChunkSchedulerTest and MultiSourceDownloadIT.
  • Documentation: Protocol reference, Architecture, Transfer lifecycle, Limitations & roadmap, Testing & evidence.

2026-09-06 — Resumable transfers via .part.meta sidecar and sequential chunk restart (Phase 2)

Feature / Transfer

  • Why: Eliminate redundant data transfer on interrupted connections by persisting verified chunk state and resuming transmission from the earliest missing chunk.
  • Behavior: Implemented TransferMeta binary sidecar format (P2PR magic, format version 1, 64-hex SHA-256, file size, chunk size, total chunks, received bitset, trailing SHA-256 checksum). Implemented TransferStorage for automatic staging discovery matching content hash and file dimensions. Added wire protocol negotiation in FILE_ACCEPT (resumed="true", resumeChunkIndex="<k>"). Sender resumes sequential transmission from chunk $k$, while receiver appends verified chunks and atomically persists .part.meta. Upon whole-file verification, both .part and .part.meta are unlinked upon publication. Corrupted metadata files fall back safely to clean transfers.
  • Compatibility/configuration: Fully backwards-compatible with non-resumed v1 transfers (omitted resume headers default to starting from chunk 0). Preserves NTFS/ext4 hard-link publication.
  • Verification: mvn -B -ntp clean verify passes 72 tests across common, tracker-server, and peer-app modules with 0 failures, including TransferMetaTest, TransferStorageTest, and ResumableTransferIT.
  • Documentation: Transfer lifecycle, Protocol reference, Limitations & roadmap, Testing & evidence.

2026-09-06 — Tracker ownership, bounded admission, and client lifetime (F-04)

Tracker / Concurrency

  • Why: Prevent duplicate peer registrations from overwriting live sessions, prevent unregister-by-key races, bound server resource consumption, and enforce deterministic shutdown (R-003, R-006).
  • Behavior: Replaced PeerRegistry.register with putIfAbsent (first-registration-wins). Conditional unregister removes only the owned PeerInfo. Duplicate registration sends ERROR message="Peer ID already registered" and closes the session. Re-registering on the same socket sends message="Already registered" and terminates. Peer list responses build an atomic snapshot. Thread pool is capped at 64 workers with SynchronousQueue. 15-second read inactivity timeout applies until registration succeeds, after which registered peers idle without timeout. Standalone shutdown computes a monotonic 5-second deadline shared across all resource closure and worker joins.
  • Compatibility/configuration: Semantic capacity remains 64 peers under tracker-v1.
  • Verification: mvn -B -ntp clean verify passes 51 tests with 0 failures, including duplicate ID rejection, unregister isolation, released ID reuse, and second-registration rejection.
  • Documentation: Architecture, Protocol reference, Testing & evidence #f-04.

2026-09-06 — Storage safety, owned staging, and atomic publication (F-06)

Storage / Correctness

  • Why: Eliminate destination race conditions, prevent overwriting existing files, and ensure unverified bytes never appear under completed filenames (R-001).
  • Behavior: Retired uniqueDestination. Implemented FileNameUtil.createPartial (creates random owned .p2p-*.part after acceptance) and FileNameUtil.publishVerified (atomic hard link via Files.createLink with automatic (n) suffix collision resolution). Removed arbitrary preallocation length (setLength). Added advisory usable space check before accepting offers. Upon successful whole-file verification, receiver atomically claims final entry, unlinks temporary partial, and emits completed update. Interrupted or mismatched receives retain the uniquely owned .part for inspection.
  • Compatibility/configuration: Deliberate local NTFS/ext4 publication contract. Retains verified partial and reports explicit failure if hard links are unsupported or denied.
  • Verification: mvn -B -ntp clean verify passes 49 tests with 0 failures, including sentinel preservation, concurrent receives to same filename, and partial retention on mismatch/interruption in StorageSafetyIT.
  • Documentation: Architecture, Transfer lifecycle, Testing & evidence #f-06.

2026-09-06 — Sequential transfer state machine and progress accounting (F-05)

Transfer / State Machine

  • Why: Enforce strict sequential stop-and-wait transfer invariants, prevent duplicate or out-of-order chunk processing, and provide truthful monotonically confirmed progress accounting (R-004, R-005).
  • Behavior: Sender validates source is a readable regular file, checks whole-file SHA-256 before completion, enforces 3-retry limit on hash rejection, and requires transfer ID matching on all responses. Receiver validates transfer ID, chunk layout (offset and length), per-chunk SHA-256, and handles repeat of immediately accepted chunk by re-acknowledging without rewriting or incrementing progress. Conflicting repeats or early completion frames are rejected. Progress percent is overflow-safe, showing 100% for completed empty files and 0% for non-completed empty state. Failure updates retain confirmed bytes rather than resetting to zero.
  • Compatibility/configuration: Preserves sequential stop-and-wait v1 transfer protocol over reliable TCP. Rejects unknown ACK statuses and malformed frames.
  • Verification: mvn -B -ntp clean verify passes 45 tests with 0 failures across the reactor, including transfer size matrix (0, 1, C, C+1, 3C+17 with Unicode filenames) and state rejection checks.
  • Documentation: Core concepts, Transfer lifecycle, Troubleshooting, Testing & evidence #f-05.

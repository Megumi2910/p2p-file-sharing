System design

One directory, many direct connections

The tracker owns presence. Each peer owns its user interface, listening socket, transfer work, and downloaded files. This boundary prevents file payloads from becoming tracker traffic.

Threads and blocking work

The tracker uses a bounded ThreadPoolExecutor capped at 64 workers with a SynchronousQueue. A peer has a daemon accept thread and bounds incoming/outgoing transfer tasks to transfer.max.concurrent (default 4) with another SynchronousQueue. Transfer progress updates are marshalled onto Swing’s event-dispatch thread. Runtime startup runs asynchronously in a SwingWorker off the EDT, with the window showing a starting state and bounded read timeouts preventing freezes.

Key design choices

Tracker presence and registration ownership (F-04)

The tracker operates strictly in memory. One registration belongs to one live control connection. The registry enforces first-live-registration-wins via putIfAbsent, rejecting duplicate peer IDs with an error and terminating the session without disturbing the active registration. Disconnect conditionally unregisters only the owned entry. Client admission is bounded by a ThreadPoolExecutor capped at TrackerProtocol.MAX_ACTIVE_PEERS = 64 with a SynchronousQueue, immediately closing sockets on overload. Read inactivity is bounded by a 15-second timeout until registration completes, after which registered peers idle without timeout.

Tracker observes the peer host

The registration message supplies a port but not an IP address. The tracker uses the source IP of the TCP connection. This reduces configuration mistakes on a host-only LAN, although it does not solve NAT traversal or machines with a different desired interface.

Random-access destination

The receiver preallocates the declared file length and writes chunks at their offsets. This prepares storage for out-of-order writes. The active sender is still a sequential push protocol; true multi-source download also needs chunk requests, a scheduler, duplicate suppression, and shared session state.

One common wire model

Both executables depend on the same frame and model classes, preventing separately maintained protocol definitions from drifting. Compatibility remains strict: only version 1 is accepted, with no negotiated fallback.

Owned staging and atomic publication

The receiver creates an owned temporary file (Files.createTempFile(".p2p-", ".part")) only after acceptance. On successful whole-file verification, it atomically publishes the final entry using hard links (Files.createLink) with automatic (n) collision avoidance on local NTFS/ext4 filesystems, never overwriting existing files. The temporary .part entry is unlinked only after publication succeeds. Interrupted or mismatched transfers retain their uniquely named .part file for diagnostics.

Failure boundaries

  • If the tracker stops, existing direct transfer sockets can continue, but peer refresh and new discovery fail.
  • If a peer disconnects normally, its tracker handler unregisters it. Abrupt disconnect is also noticed when a read reaches EOF.
  • If a remote endpoint stays connected but silent, phase read timeouts (15s read, 120s prompt, 135s response, 300s verify) terminate the session cleanly.
  • If a transfer fails after destination creation, its uniquely owned .part file remains for diagnostic inspection.
  • Active transfer sockets are tracked in a package-private TransferSession and are explicitly closed during two-phase shutdown under a shared monotonic 5-second deadline.

Peer admission and shared shutdown (F-07)

Transfer concurrency is bounded by a ThreadPoolExecutor capped at transfer.max.concurrent (default 4) with a SynchronousQueue. Excess incoming connections close immediately, and excess outgoing requests report busy without blocking the EDT. Sockets are tracked in a package-private TransferSession. Two-phase teardown uses a single monotonic 5-second deadline (System.nanoTime() + 5s) shared across all worker and acceptor joins. Startup runs asynchronously off the EDT, with rollback closing all acquired resources on failure.

Foundation architecture contracts (planned changes)

This section records the target architecture contracts established in the Project foundation and execution plan. The current baseline behavior is documented above; the contracts below govern the stabilization repairs.

Protocol boundary and limit ownership (F-03)

Planned

Protocol limits belong to dedicated constant owners: TransferProtocol.DEFAULT_CHUNK_BYTES (1 MiB), TransferProtocol.MAX_CHUNK_BYTES (8 MiB), TrackerProtocol.MAX_ACTIVE_PEERS (64), TrackerProtocol.MAX_PEER_LIST_PAYLOAD_BYTES (1 MiB), and FrameIO.MAX_PAYLOAD_BYTES (64 MiB). Value validation belongs to model records (FileMetadata, PeerInfo), which enforce nonblank strings, canonical UUIDs, port ranges, and reject ISO controls.

Sequential transfer and verified state (F-05)

Planned

Sequential stop-and-wait transfer strictly matches offered transfer ID and chunk index. Receiver verifies exact expected offset, length, and per-chunk SHA-256 before writing. Replays of the immediately preceding chunk are recognized and re-acknowledged without rewriting. Progress counters are monotonically confirmed.

Owned staging and publication (F-06)

Planned

Receiver creates a unique, owned partial file (Files.createTempFile(".p2p-", ".part")) per session. On successful whole-file verification, it atomically publishes the entry using hard links (Files.createLink) with collision-avoidance suffixes (name (n).ext) on local NTFS/ext4, never overwriting existing files.

Tracker ownership and lifetime (F-04)

Planned

Tracker uses putIfAbsent for first-live-registration-wins, closes sessions attempting duplicate IDs, builds atomic snapshots for peer lists, and enforces a bounded ThreadPoolExecutor (max 64) with SynchronousQueue.

Peer admission, timeouts, and shutdown (F-07)

Planned

Bounded transfer concurrency (max 4). Strict phase timeouts with transferOfferResponseTimeoutMillis > transferPromptTimeoutMillis. Single monotonic 5-second deadline shared across all component shutdown joins. EDT-safe asynchronous startup.

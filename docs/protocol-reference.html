Binary framing and messages

Protocol version 1 wraps typed messages in a length-delimited binary frame. All multibyte numbers use Java DataOutputStream/DataInputStream big-endian representation.

Frame layout

OrderFieldEncodingValidation on read
1Magic4-byte signed integer 0x50325031 (“P2P1”)Exact match
2Version2-byte signed short, value 1Exact match; no negotiation
3Message type4-byte integerMust map to a known enum code
4Header count4-byte integer0–128 inclusive
5HeadersRepeated key/value pairs via Java writeUTFStream decoding; duplicate keys rejected with IOException
6Payload length4-byte integer0–67,108,864 bytes
7PayloadExactly payload-length raw bytesreadFully rejects premature EOF
String compatibility: Java writeUTF uses modified UTF-8 with an unsigned two-byte encoded-length prefix. A client in another language must implement that format exactly; ordinary UTF-8 with a four-byte length is incompatible.

Peer-list payload

The payload begins with a 4-byte peer count. Every peer then contains peerId, displayName, and host as Java modified-UTF strings followed by a 4-byte port. Decode accepts 0–10,000 entries but does not reject trailing bytes, invalid ports, duplicate IDs, or blank values.

Compatibility rules for future changes

Changing a code, field order, string representation, or header meaning changes the wire contract. Additive headers are usually tolerated because unknown headers remain in a map, but a receiver may still require a newly added field. Any incompatible change should increment the protocol version and document mixed-version behavior before implementation.

Source of truth: MessageType, FrameIO, PeerListCodec, FileMetadata, tracker and transfer handlers.

End-to-end workflow

From selected file to verified file

A transfer is sender-driven and sequential. The receiver decides whether to accept, verifies each chunk before acknowledging it, and publishes the file only after a complete SHA-256 match.

Normal path in detail

  1. Select and prepare. The UI passes the chosen path and target peer to TransferManager. A background FileSender creates a random transfer ID, reads the file size, reports PREPARING, and hashes the entire file.
  2. Describe the content. The sender calculates ceil(fileSize / chunkSize). The full hash becomes both fileId and fileSha256; the current design treats content identity and expected digest as the same value.
  3. Connect directly. The sender connects to the target’s advertised host/port with a 7-second connect timeout and disables Nagle buffering with TCP_NODELAY. Phase read inactivity timeouts apply (15s read, 120s prompt, 135s response, 300s verify).
  4. Offer and decide. FILE_OFFER carries metadata. Bob either sees a synchronous Swing question or auto-accepts from configuration. Rejection sends FILE_REJECT and creates no destination.
  5. Choose storage. Acceptance sanitizes the offered name to a base filename and finds a currently unused destination. The receiver creates the download directory, derives finalName.part, returns FILE_ACCEPT, and stages an owned .p2p-*.part file without arbitrary length preallocation.
  6. Send chunks. For each index, the sender reads the expected range, hashes that byte array, and sends CHUNK_DATA. The receiver checks the hash and bounds, seeks to the offset, writes, and replies with CHUNK_ACK.
  7. Retry corruption. A hash mismatch produces status=RETRY without writing. The sender makes at most three attempts. Unexpected response types or exhausted retries fail the transfer.
  8. Verify and publish. After all chunks are acknowledged, the sender sends TRANSFER_COMPLETE. The receiver closes its writer, hashes the temporary file, and compares the result with the offer. A match moves it to the final path, preferring an atomic move.

Phase timeouts and cancellation (F-07)

Transfers are bounded by distinct phase timeouts: 120-second prompt budget, 135-second sender response wait (leaving 15 seconds network/scheduling overhead), 15-second active read timeout, and 300-second verification timeout. If prompt expires, receiver sends rejection. If response timeout elapses, sender fails with a read timeout. Local application shutdown terminates active transfers as CANCELLED.

Boundary cases

Empty file

The sender calculates zero chunks, sends no CHUNK_DATA, then immediately sends completion. The receiver’s zero-length temporary file hashes to the standard SHA-256 value for empty content and can complete normally. Focused localhost verification passed this path.

Partial final chunk

The final read length is the smaller of configured chunk size and remaining bytes. Its offset is still index × chunkSize, so it ends exactly at the declared file size.

Duplicate or misleading chunks

Repaired in F-05 The receiver enforces strict sequential state: chunkIndex == nextChunkIndex. Repeats of the immediately preceding chunk (chunkIndex == nextChunkIndex - 1) are recognized and re-acknowledged with CHUNK_ACK OK without rewriting or incrementing progress if and only if their payload SHA-256 matches the last accepted digest. Conflicting repeats or out-of-order chunks terminate the session. Early TRANSFER_COMPLETE before all chunks are received is rejected.

Destination collision

Repaired in F-06 Each transfer creates an isolated temporary file (.p2p-*.part). Upon whole-file verification, FileNameUtil.publishVerified atomically claims the final filename via hard link (Files.createLink). If the destination already exists (including existing files or concurrent transfers), it increments suffix (1), (2), etc., preventing overwrite and guaranteeing distinct publication.

Interrupted connection

EOF or another exception produces FAILED. The partial file remains, but there is no bitmap or metadata from which to resume. If a connection stays open without data, the phase read inactivity timeout triggers (15s read, 120s prompt, 135s response), failing the transfer cleanly.

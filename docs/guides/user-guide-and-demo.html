In-app Settings dialog

Modeless configuration surface replacing the legacy read-only dialog. Allows editing display name, port, tracker host/port, directory paths (with native browse dialogs and path resolution previews), auto-accept, and startup update checking. Features a collapsible Advanced section for transfer parameters (chunk size, timeouts, concurrency bounds). Persists atomically with optimistic conflict detection; running runtime continues unaffected until an explicit, idle-verified restart.

Software updates dialog and toolbar

Dedicated update toolbar below the header with status badge. The Software Updates dialog connects to GitHub Releases, downloads signed peer-app.jar packages with real-time progress, validates Ed25519 signatures and SHA-256 digests, and initiates atomic replacement with automatic rollback on launch failure.

Complete classroom demonstration

  1. Prepare. Choose a recognizable multi-chunk file and calculate its SHA-256 on Alice.
  2. Start the tracker. Confirm the Windows console says it is listening on port 5000.
  3. Start Alice, then Bob. Confirm their listening ports and tracker-observed addresses in logs.
  4. Refresh both windows. Alice should list Bob and Bob should list Alice.
  5. Send from Alice. Select Bob, click Send file…, and watch PREPARING while hashing.
  6. Accept on Bob. Explain that this is a direct peer decision; the tracker is absent from the data connection.
  7. Observe. Point out progress and chunk states. Bob publishes the final name only after verification.
  8. Prove integrity. Confirm COMPLETED, no .part suffix, and matching SHA-256.
  9. Show rejection. Send again and reject; both sides report REJECTED and no completed file appears.
  10. Show presence. Close Bob and refresh Alice; the tracker’s online list is memory-backed.

Suggested explanation

“The tracker is a directory, not a relay. It returns peer addresses. Alice then creates a separate TCP connection directly to Bob. Bob verifies every chunk before acknowledging it and exposes the final file only after its complete SHA-256 matches.”

Likely questions

Why hybrid P2P?
Discovery is centralized; file delivery is peer-to-peer.
Can the tracker read the file?
No file payload is sent on the implemented tracker path.
Can chunks arrive out of order?
Storage supports offsets, but the active sender sends sequentially.
Is SHA-256 authentication?
No. It compares bytes with sender-announced hashes; the transport has no identity proof or encryption.
Can transfers resume?
No persisted chunk state or resume protocol exists.
Demo honesty: handbook simulations explain behavior but do not replace a real three-machine run. Record actual IPs, versions, hashes, and results as environmental proof.

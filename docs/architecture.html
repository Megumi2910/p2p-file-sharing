System design

One directory, many direct connections

The tracker owns presence. Each peer owns its user interface, listening socket, transfer work, and downloaded files. This boundary prevents file payloads from becoming tracker traffic.

The two connection types have different lifetimes. Each peer keeps one tracker socket from registration until disconnect. Each file send opens a new peer-to-peer socket and closes it when the transfer succeeds, is rejected, or fails.

Threads and blocking work

The tracker’s main thread blocks in ServerSocket.accept(); each accepted client is submitted to a cached executor. A peer has a daemon accept thread and submits each incoming receiver plus every outgoing sender to another cached executor. Transfer events are marshalled onto Swing’s event-dispatch thread before updating the table.

Startup exception: runtime.start() is called from Swing’s event thread. Starting the peer server and waiting for tracker registration therefore happen before the window becomes visible. A slow tracker can freeze startup because socket reads do not have a read timeout.

Key design choices

Tracker observes the peer host

The registration message supplies a port but not an IP address. The tracker uses the source IP of the TCP connection. This reduces configuration mistakes on a host-only LAN, although it does not solve NAT traversal or machines with a different desired interface.

Random-access destination

The receiver preallocates the declared file length and writes chunks at their offsets. This prepares storage for out-of-order writes. The active sender is still a sequential push protocol; true multi-source download also needs chunk requests, a scheduler, duplicate suppression, and shared session state.

One common wire model

Both executables depend on the same frame and model classes, preventing separately maintained protocol definitions from drifting. Compatibility remains strict: only version 1 is accepted, with no negotiated fallback.

Temporary file before publication

The final filename appears only after whole-file verification. This keeps incomplete content visibly separate. The tradeoff is that interrupted .part files need manual cleanup today because resume metadata is not implemented.

Failure boundaries

  • If the tracker stops, existing direct transfer sockets can continue, but peer refresh and new discovery fail.
  • If a peer disconnects normally, its tracker handler unregisters it. Abrupt disconnect is also noticed when a read reaches EOF.
  • If a remote endpoint stays connected but silent, current reads can block indefinitely.
  • If a transfer fails after destination creation, its .part file remains.
  • Closing an executor interrupts tasks, but blocking socket reads are not guaranteed to end because active transfer sockets are not centrally tracked and closed.

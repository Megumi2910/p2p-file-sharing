Foundations

The ideas behind the transfer

The program combines a small centralized directory with direct peer connections. Understanding the boundary between those jobs makes the rest of the source much easier to read.

Addresses, ports, and sockets

An IP address identifies a network interface. A TCP port identifies a listening program on that host. Together, 192.168.56.102:6002 tells Alice where Bob’s peer server accepts connections. A TCP socket is one live connection between two endpoints.

TCP is a byte stream. One call that writes a frame is not guaranteed to match one low-level network packet or one read. FrameIO therefore writes lengths and uses readFully for the payload.

Frames: messages on top of TCP

TCP does not know what a “file offer” is. The application creates that meaning with a frame: magic bytes, protocol version, message type, a map of text headers, payload length, and payload bytes. The magic and version reject unrelated or incompatible streams early. Length fields tell the reader exactly how many bytes belong to each section.

Chunks and offsets

A chunk is a bounded portion of a file. With a 1 MiB chunk size, a 2.5 MiB file becomes two full chunks and one half-size chunk. Each offset is the destination position where that chunk begins. The receiver uses RandomAccessFile.seek(offset), which allows out-of-order writing in principle even though the current sender sends sequentially.

Integrity, identity, and confidentiality

Peer identity hygiene and tracker capacity

Peer IDs and display names reject ISO control characters (C0 and C1 controls including NUL, LF, CR, TAB, and DEL) before trimming. Ordinary Unicode (such as Vietnamese or Japanese names) is fully preserved without ASCII restriction. In addition, Tracker-v1 defines a shared semantic capacity of TrackerProtocol.MAX_ACTIVE_PEERS = 64 peers, distinct from the defensive 10,000-record codec ceiling.

SHA-256 maps bytes to a fixed-length digest. The sender hashes each chunk and the full file. The receiver recomputes hashes and compares them, detecting accidental corruption or altered bytes. In this project, the whole-file hash also serves as fileId, while a random transferId identifies one sending session.

ACKs, retries, and completion

TCP already supplies ordered stream delivery, transport retransmission, duplicate suppression, and transport checksum checks. CHUNK_ACK OK instead confirms that the application parsed a complete frame, matched its transfer ID, chunk index, and layout, validated its SHA-256, and accepted a unique write into transfer state (or recognized the immediately previous accepted chunk). It does not promise fsync durability or whole-file publication. RETRY requests application retransmission only after hash rejection; three total attempts remain, with no timeout reconnect. SHA-256 compares bytes to the sender's claim; it is not peer authentication.

Concurrency vocabulary

Race condition
The result depends on timing. Two receivers can both observe that the same filename is free before either creates its temporary file.
Thread pool
A service that runs transfer or client tasks concurrently. Both tracker clients (capped at 64) and peer transfers (capped at transfer.max.concurrent, default 4) use bounded thread pools with a SynchronousQueue.
Synchronization
Tracker client operations are synchronized so two UI actions cannot mix request/response frames on one socket.
Idempotency
Repeating an operation has the same effect as doing it once. Under F-05, repeating an immediately accepted chunk re-acknowledges with CHUNK_ACK OK without rewriting or inflating progress.

Build and operate

Prepare the tracker and two peers

The intended classroom topology places the tracker on Windows and one Swing peer on each Ubuntu Desktop VM. All three machines must share a reachable private or host-only network.

Prerequisites

  • JDK 21 on the build machine and Java 21 runtime on every machine running a JAR.
  • Maven 3.9 or newer on the build machine.
  • Ubuntu Desktop or another graphical Linux session for Swing peers.
  • A host-only/private adapter permitting VM → host and VM → VM traffic.
java -version
mvn -version

Latest local evidence: JDK 21 compiled all sources. Maven was unavailable, so the documented package command remains source-configured but not locally re-verified.

Build from the repository root

mvn clean package

The parent reactor builds common, then shaded executable JARs:

tracker-server/target/tracker-server.jar
peer-app/target/peer-app.jar

Start the tracker on Windows

java -jar .\tracker-server\target\tracker-server.jar 5000

Port 5000 is the default. The server binds on all local interfaces through new ServerSocket(port). If Windows Firewall prompts, allow Java on the relevant private network. The provided run-tracker-windows.bat assumes it is launched from the repository root because its JAR path is relative.

Expected log:

[TRACKER] Listening on 0.0.0.0:5000

Configure each peer

Copy peer-app/src/main/resources/peer.properties.example beside the peer JAR as peer.properties. Relative download paths resolve from the process working directory, not from the properties file’s directory.

PropertyRequired/defaultMeaning and current validation
peer.idRequired, nonblankRegistry key. Must be unique operationally, but duplicate IDs are currently accepted.
peer.nameRequired, nonblankHuman label shown in peer lists and offers.
peer.portDefault 6001Local listening TCP port. Parsed as integer; valid port range is not checked before binding.
tracker.hostDefault 127.0.0.1Windows host-only address as seen from the VM.
tracker.portDefault 5000Tracker TCP port; integer parsing only.
download.dirDefault downloadsDestination folder; created when receiving.
chunk.size.bytesDefault 1048576Sender chunk size. Must be positive in practice, but no explicit configuration validation exists.
transfer.autoAcceptDefault falsetrue bypasses the incoming-file question; any other text parses as false.

Alice

peer.id=peer-a
peer.name=Alice
peer.port=6001
tracker.host=192.168.56.1
tracker.port=5000
download.dir=downloads
chunk.size.bytes=1048576
transfer.autoAccept=false

Bob

peer.id=peer-b
peer.name=Bob
peer.port=6002
tracker.host=192.168.56.1
tracker.port=5000
download.dir=downloads
chunk.size.bytes=1048576
transfer.autoAccept=false

Verify the network before Java

On Windows, use ipconfig to identify the host-only adapter. On both VMs:

ip a
ping 192.168.56.1

After Bob is listening, test his port from Alice:

nc -vz <BOB_VM_IP> 6002

Also verify that neither peer port is already in use and that VM firewalls permit inbound TCP. Different VMs may technically use the same port, but distinct ports make logs and demonstrations clearer.

Start peers

java -jar peer-app.jar peer.properties

The provided run-peer-linux.sh runs exactly that command and therefore expects both files in the current directory. Startup first binds the peer port, then connects and registers with the tracker. Expected logs include:

[PEER] Listening for P2P transfers on 0.0.0.0:6001
[PEER] Tracker sees this peer as 192.168.56.101:6001
Startup cleanup gap: if peer binding succeeds but tracker registration fails, the startup error is shown but the partially created runtime is not explicitly closed in that failure path. End the process before retrying to ensure the port is released.

Stop and restart

Closing the Swing window exits the process; shutdown hooks attempt to disconnect and close runtime services. Stop peers before the tracker for clean unregistration. After an abnormal stop, wait for the operating system to release ports and remove unwanted .part files only after confirming no transfer process is still using them.

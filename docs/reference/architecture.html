System design

One directory, many direct connections

The tracker owns presence. Each peer owns its user interface, listening socket, transfer work, and downloaded files. This boundary prevents file payloads from becoming tracker traffic.

Threads and blocking work

The tracker uses a bounded ThreadPoolExecutor capped at 64 workers with a SynchronousQueue. A peer has a daemon accept thread and bounds incoming/outgoing transfer tasks to transfer.max.concurrent (default 4) with another SynchronousQueue. Transfer progress updates are marshalled onto Swing’s event-dispatch thread. Runtime startup runs asynchronously in a SwingWorker off the EDT, with the window showing a starting state and bounded read timeouts preventing freezes.

Key design choices

Tracker presence and registration ownership (F-04)

The tracker operates strictly in memory. One registration belongs to one live control connection. The registry enforces first-live-registration-wins via putIfAbsent, rejecting duplicate peer IDs with an error and terminating the session without disturbing the active registration. Disconnect conditionally unregisters only the owned entry. Client admission is bounded by a ThreadPoolExecutor capped at TrackerProtocol.MAX_ACTIVE_PEERS = 64 with a SynchronousQueue, immediately closing sockets on overload. Read inactivity is bounded by a 15-second timeout until registration completes, after which registered peers idle without timeout.

Tracker observes the peer host

The registration message supplies a port but not an IP address. The tracker uses the source IP of the TCP connection. This reduces configuration mistakes on a host-only LAN, although it does not solve NAT traversal or machines with a different desired interface.

Random-access destination

The receiver preallocates the declared file length and writes chunks at their offsets. This prepares storage for out-of-order writes. The active sender is still a sequential push protocol; true multi-source download also needs chunk requests, a scheduler, duplicate suppression, and shared session state.

One common wire model

Both executables depend on the same frame and model classes, preventing separately maintained protocol definitions from drifting. Compatibility remains strict: only version 1 is accepted, with no negotiated fallback.

Owned staging and atomic publication

The receiver creates an owned temporary file (Files.createTempFile(".p2p-", ".part")) only after acceptance. On successful whole-file verification, it atomically publishes the final entry using hard links (Files.createLink) with automatic (n) collision avoidance on local NTFS/ext4 filesystems, never overwriting existing files. The temporary .part entry is unlinked only after publication succeeds. Interrupted or mismatched transfers retain their uniquely named .part file for diagnostics.

Shared-file catalogue and search (Phase 3)

Peers index a local shared folder (shared.dir) and publish content metadata (SHA-256 fileId, name, size, chunks) to the tracker via TRACKER_PUBLISH_FILES. The tracker maintains an in-memory FileCatalogue associating each content ID with live provider peer IDs. When a peer disconnects, its entries are pruned automatically. Search queries (TRACKER_SEARCH) resolve active providers via PeerRegistry; selecting a search result initiates direct P2P transfer via FILE_REQUEST without routing file bytes through the tracker.

Multi-source concurrent download (Phase 4)

Downloader-driven multi-source transfer is coordinated by MultiSourceDownloader and a dynamic ChunkScheduler. The downloader partitions missing chunks across available provider peers, streaming chunks concurrently over direct TCP connections (bounded to transfer.max.concurrent). Each CHUNK_REQUEST specifies the catalogue's agreed chunk size so providers with different local defaults serve the identical byte range. If a provider peer disconnects, times out, or returns a corrupted chunk, the scheduler transparently marks that peer failed and reassigns its missing chunks to surviving providers. Chunks are written safely to the shared .part file with synchronized random-access seeks and atomic .part.meta updates, followed by final whole-file verification and atomic hard-link publication.

Demonstration polish, metrics, and chunk visualization (Phase 5)

The desktop user interface (MainFrame) uses FlatLaf styling with process-local Light and Dark theme switching, managed by DesktopTheme and customized via FlatLaf.properties. It features a three-tab workspace: active Transfers, Catalogue Search, and an Activity Log for timestamped auditing. The header exposes an owned Peer details dialog and session theme selector. The transfers table displays truthful speed, estimated time to completion (ETA), and active source counts with 36px row heights, custom progress bars, and semantic status colors. An integrated ChunkVisualizerPanel inspector displays full transfer metadata and an honest bounded 64-bucket chunk coverage strip (Received, Partial range, Missing), with graceful fallback for unchunked transfers. The entire transfer state, chunk bitmask, and source count are decoupled from UI threads and marshaled safely through SwingUtilities.invokeLater.

In-app configuration store and atomic persistence

Atomic snapshot-based file catalogue (2026-09-11)

The tracker's FileCatalogue maintains a concurrent map of provider peer IDs to immutable List<FileRecord> snapshots. Each publication atomically replaces only that provider's snapshot, and peer removal deletes only its entry. For search, the tracker obtains a live registry snapshot once, groups active publications by content SHA-256 hash, and emits one result per matching hash with all live registered providers. Displayed metadata is selected deterministically: case-insensitive filename, then exact filename, then peer ID. For hash or empty queries, this deterministic ordering applies to all records of that hash. Duplicate-content aliases within provider snapshots are retained so that renaming or removing an alias updates search results correctly without affecting other providers sharing identical content. In TrackerServer.handleClient(), the owned peer's catalogue is removed before releasing its registry registration, preventing an old session's disconnect handler from deleting a newly reconnected session's publication for the same ID.

Hybrid local folder synchronization (SharedFolderIndexer & SharedFolderMonitor)

Local folder synchronization operates in a hybrid model: automatic indexing and publication of filesystem changes via NIO WatchService, combined with an explicit manual rescan action.

  • Authoritative indexer (SharedFolderIndexer): Exclusively owned by a scheduled scan worker, caching each eligible top-level file's key, size, last-modified timestamp, and FileRecord. Per-path dirty generations are tracked atomically so events arriving during hashing remain marked dirty for subsequent passes. Normal scans rehash only changed or event-invalidated files. New and modified files require two equal attribute observations at least one second apart before hashing. Attributes and generations are re-checked immediately before and after SHA-256 calculation; any mid-hash modification aborts publication and keeps the file pending. Confirmed missing directories yield an empty snapshot and a warning, withdrawing unavailable files once connected, while enumeration errors retain the last complete snapshot.
  • Lifecycle monitor (SharedFolderMonitor): Runs a dedicated daemon watcher thread that drains and resets watch keys around the initial scan to avoid startup race gaps. Event bursts are coalesced with a 1-second quiet period and a 5-second maximum batch delay. If the watch key is invalidated, watching is unsupported, or registration fails, the monitor automatically switches to a 5-second polling reconciliation with visible degraded-mode details and retries watch registration when the directory is available. Concurrent rescan() invocations coalesce onto a single active future.

Tracker resilience and decoupled direct transfers

Tracker discovery is decoupled from peer-to-peer data transfers within PeerRuntime:

  • Dedicated control executor: A single-threaded scheduled executor owns tracker registration, periodic discovery, and catalogue publication, keeping file hashing strictly on the monitor worker and GUI operations on the EDT. Helper methods prevent scheduled tasks from blocking on themselves.
  • Periodic discovery and dead-connection detection: After initial startup, PeerRuntime issues TRACKER_LIST_PEERS every 5 seconds (fixed delay after completion). A successful list updates the cached peer list and timestamp; a failed list never clears the cache.
  • Outage recovery and bounded backoff: On connection failure, the tracker state transitions to OFFLINE, preserving previously discovered peers and local metadata. The runtime automatically reconnects with exponential backoff delays of 1, 2, 4, 8, then 15 seconds. Manual peer refresh requests trigger an immediate attempt without spawning parallel recovery loops.
  • Catalogue revision tracking: Local catalogue revisions are tracked monotonically, while acknowledged revisions are tracked per connection. Reconnection invalidates prior acknowledgements and republishes the latest valid snapshot. Publications preflight item limits (CatalogueCodec.MAX_CATALOGUE_ITEMS = 10,000) and payload limits (TrackerProtocol.MAX_PEER_LIST_PAYLOAD_BYTES = 1 MiB); oversized catalogues enter local error state without silent truncation or reconnect churn.
  • Direct transfer continuity: While the tracker is offline, new global searches fail explicitly, but previously cached peers and search results remain fully usable for direct sends and multi-source downloads.

Configuration management is decoupled from runtime startup through ConfigStore. The running PeerRuntime retains its immutable AppConfig instance throughout its lifetime, ensuring settings changes never mutate live listeners, directory watchers, or auto-accept flags unpredictably.

  • Atomic persistence: Edits are merged over original properties, preserving unknown keys and values. Persistence normalizes comments and key ordering according to standard java.util.Properties store semantics. Writes flush to a forced temporary file in the same directory and execute an atomic move (ATOMIC_MOVE with REPLACE_EXISTING), guaranteeing that original configuration bytes remain intact if a failure occurs.
  • Concurrency and conflict detection: Settings writers serialize within the JVM via a dedicated monitor and across processes via an exclusive FileChannel lock on a sibling <configFileName>.lock file. Target existence, symlink target resolution, and content SHA-256 digests are verified under the lock and immediately before publishing. Optimistic concurrency control detects racing external modifications and triggers ConfigConflictException, preserving user drafts and providing explicit reload options rather than permitting silent overwrites.
  • Relative path semantics: Path values in configuration remain relative to the process working directory, not the configuration file directory, ensuring consistent behavior across standalone launchers and IDE launches.

Signed release distribution and safe out-of-process updates

Client distribution is decoupled from Git and Maven dependencies, packaging an end-user bundle containing only the runtime JAR, platform launchers, and example settings.

  • Asymmetric release trust: Updates are authenticated using Java standard Ed25519 signatures. The client embeds the owner's public key (X.509 base64); private keys are confined to GitHub Actions release secrets and operator key stores. A strict JSON manifest contract defines required artifacts, exact sizes (≤128 MiB), lowercase 64-hex SHA-256 hashes, Java requirements (minJava 21), and installer protocol (version 1).
  • Bounded network client: ReleaseClient queries fixed GitHub Releases endpoints using strict streaming JsonReader in STRICT mode. Initial download URLs must strictly match GitHub release asset paths; up to five HTTPS redirects are permitted, restricted to a strict whitelist (github.com, release-assets.githubusercontent.com, objects.githubusercontent.com) with non-443 port and IP literal rejection. Downloads stream through 64 KiB buffers with incremental SHA-256 digest calculation; cancellations or timeouts delete partial files immediately.
  • Atomic idle admission gate: Settings restarts and update installations require atomic reservation on TransferManager.tryReserveRestart(). Under lifecycle lock, reservation succeeds only when active transfer sessions and pending incoming file prompt decisions are completely empty. While reserved, all submission paths reject new transfers and racing sockets close immediately.
  • Out-of-process helper lifecycle: Because running JARs cannot be replaced in-place on Windows without file locking errors, the client copies the running JAR to .p2p-update/helper.jar and launches UpdateInstaller. The helper acquires operation.lock, confirms parent identity, and signals readiness (P2P_HELPER_READY). Once the parent reserves idle status, cleanly stops PeerRuntime, and signals GO, the helper acquires exclusive runtime.lock, moves the current JAR to previous.jar, moves candidate.jar to peer-app.jar, and spawns the child with --update-bootstrap. Local bootstrap readiness (P2P_BOOTSTRAP_READY) is verified before committing (COMMIT); pre-acknowledgment failures trigger automatic rollback to previous.jar.

Failure boundaries

  • If the tracker stops, previously discovered peers and search results remain cached and usable for direct P2P transfers and chunk downloads; new discovery and new catalogue searches fail explicitly with inline warnings rather than clearing cached state or opening modal dialogs. The runtime automatically reconnects with bounded exponential backoff when the tracker recovers and republishes the latest catalogue snapshot.
  • If a peer disconnects normally, its tracker handler removes its catalogue snapshot before unregistering it from the registry. Abrupt disconnect is also noticed when a read reaches EOF.
  • If a remote endpoint stays connected but silent, phase read timeouts (15s read, 120s prompt, 135s response, 300s verify) terminate the session cleanly.
  • If a transfer fails after destination creation, its uniquely owned .part file remains for diagnostic inspection.
  • Active transfer sockets are tracked in a package-private TransferSession and are explicitly closed during two-phase shutdown under a shared monotonic 5-second deadline.

Current truth and planned direction

Stabilize before expanding

The application is appropriate for a trusted-LAN demonstration. Reliability and protocol validation should be completed before resume, catalog search, or multi-source scheduling adds more states.

Roadmap with dependencies

Phase 1 — reliable current transfer

Completed Fixed R-001 through R-007 across F-01A–F-07, added 63 committed reactor tests, verified phase timeouts, atomic hard-link publication, bounded admission, and safe shutdown. This provides the stable foundation for Phase 2 resumable transfers.

Phase 2 — resumable chunks

Completed Implemented binary .part.meta sidecar persistence with trailing SHA-256 checksums, automatic resumable staging discovery in TransferStorage, and resume negotiation in FILE_ACCEPT (resumed="true", resumeChunkIndex). Sender skips contiguous verified chunks and resumes sequential transmission seamlessly. Both temporary files are unlinked upon publication.

Phase 3 — shared-file catalogue

Completed Implemented FileRecord, SearchResult, binary CatalogueCodec, local folder indexing in SharedFolderIndexer, and in-memory FileCatalogue on the tracker. Search queries match filenames and content IDs case-insensitively, returning live providers. Disconnecting peers automatically prunes stale catalogue entries. Downloader initiates direct transfer from search results via FILE_REQUEST.

Phase 4 — true multi-source download

Completed Implemented CHUNK_REQUEST wire protocol, ChunkScheduler dynamic allocation with duplicate-request prevention, and MultiSourceDownloader concurrent multi-peer streaming with automatic peer failover. Verified in MultiSourceDownloadIT that chunks stream in parallel from multiple providers and survive source drops, finishing with exact whole-file SHA-256 equality.

Phase 7 — Tracker resilience, hybrid folder synchronization, and desktop UX Implemented

Implemented atomic snapshot-based catalogue indexing on the tracker (FileCatalogue) with deterministic metadata selection, alias retention, and disconnect unregistration sequencing. Implemented hybrid local shared-folder synchronization in SharedFolderIndexer and SharedFolderMonitor (authoritative attribute caching, dirty generations, two-observation stability detection ≥1s, and pre/post hash verification). Implemented dedicated single-threaded control executor and tracker recovery loop with exponential backoff (1, 2, 4, 8, 15s) in PeerRuntime, decoupling direct transfers from discovery outages. Modernized desktop UX in MainFrame with Local Sharing strip, wrapping peer status, two-row search toolbar layout, retained search results during outages, sender display in incoming prompts, and unsaved settings draft loss protection in SettingsDialog. Repaired DesktopUiSmoke with zero synthetic clicks and verified across all four display scales (1, 1.25, 1.5, 2).

Phase 6 — Client releases, in-app settings, and safe updates Implemented

Eliminated Git and Maven dependencies for end users by publishing self-contained p2p-client-VERSION.zip releases with platform launchers (run-peer-windows.bat and run-peer-linux.sh). Replaced the read-only peer details dialog with an in-app Settings dialog supporting atomic configuration persistence, directory browsing, relative path preservation, and optimistic conflict detection. Implemented in-app software update discovery, Ed25519 manifest and binary verification, atomic idle restart reservation on TransferManager, and out-of-process helper replacement with automatic rollback.

Phase 5 — demonstration polish Implemented

Truthful speed/ETA, active source count, real-time chunk visualization panel (green blocks for verified chunks, gray for pending), timestamped in-memory Activity Log tab, and complete failover demonstration scenario (Alice drops mid-stream, Bob continues without data loss) are implemented and verified via ClassroomDemoScenarioIT and fresh Swing screenshots.

Security boundary

The release update subsystem establishes executable binary authenticity via asymmetric Ed25519 digital signatures verified against embedded public trust keys. However, this signing protects only the downloaded release artifacts from GitHub. The runtime P2P file transfers, tracker discovery, and inter-peer communication remain unencrypted on a controlled private network (LAN/VPN). SHA-256 detects payload corruption or inconsistency with the sender’s claim, but does not provide peer confidentiality or transport authentication. Do not expose tracker or peer ports to an untrusted network as if they were production services.

Known operational limits (Phase 7)

  • Top-level folder scope: Shared folder synchronization monitors the configured directory top-level; recursive directory trees are not indexed.
  • Eventual consistency on writer pauses: Stability detection requires two matching attribute observations at least one second apart. A slow writer pausing longer than the quiet period may be hashed before completion; end-to-end hash verification protects receivers, and copying to excluded *.part before renaming is recommended for atomic writer availability.
  • Session-lifetime peer memory: Discovered peers remain cached in memory during tracker outages for the duration of the running session; cached peers are not persisted across application restarts.

Revisit architecture when

  • Peers operate behind NAT or across the public internet.
  • Users require authenticated identity, authorization, private transfers, or audit history.
  • The tracker must survive restart or scale beyond one in-memory process.
  • Multi-source scheduling or large concurrency makes one thread per session unsuitable.
  • Cross-language clients require a deliberately portable string encoding and version negotiation.

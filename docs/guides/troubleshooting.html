Symptom-first diagnosis

Find which boundary failed

Check process, route, port, and protocol in that order. Preserve console output and the exact UI message before restarting; the application has no persistent diagnostic history.

Fast network ladder

  1. Can each VM see its own IP with ip a?
  2. Can each VM ping the Windows host-only IP?
  3. Is the tracker listening on Windows port 5000?
  4. Does each peer log a tracker-observed address?
  5. Can Alice open Bob’s peer port with netcat?
  6. Does refresh cause a tracker request and response?

Partial files

A .part file means publication did not finish. The application cannot resume it and does not automatically delete it. Before deletion, ensure no peer process is using it. Its allocated length may equal the advertised final size even when many ranges were never received because setLength preallocates it.

Truthful progress reporting (F-05): Confirmed byte counts represent matched acknowledgements on the sender and unique verified writes on the receiver. On failure, confirmed bytes are never reset to zero. Progress calculation ensures that completed empty files show 100%, and uncompleted empty files show 0%, with no integer overflow or inflated percentages.

Do not infer integrity from size or 100% progress. Only a successful whole-file SHA-256 and final rename prove the current receiver accepted the completed content.

Configuration and Settings issues

Conflict: configuration was modified externally
The in-app Settings dialog uses optimistic concurrency control with SHA-256 digests. If an external editor or another process modifies peer.properties while the dialog is open, saving is rejected to avoid silent overwrites. The dialog preserves your draft edits and displays an explicit "Reload from disk" button so you can inspect external changes before choosing to reload or re-save.
Configuration parent directory is not writable
The configuration file directory must be writable to allow temporary file creation and atomic replacement. Check folder permissions if running on a shared multi-user system.

Update, restart, and recovery troubleshooting

Active transfers or prompt decisions are in progress. Restart refused.
To protect data integrity, restarts (both for settings application and update installations) require zero active transfer sessions and no pending incoming file prompt decisions. Complete or cancel active transfers before attempting restart.
Save or cancel settings first
Restarting the application (for software updates or settings changes) is refused while the Settings dialog has unsaved draft changes. Save or cancel your pending settings edits before initiating a restart.
Stopped — relaunch manually
If an error occurs during runtime shutdown or helper process handoff after networking services have stopped, the runtime cannot be safely resumed or restarted in-place. The main window transitions to a disabled "Stopped — relaunch manually" state displaying the configuration file path and working directory. Close the application and relaunch it manually to restore clean service initialization.
An update installation is currently in progress
Only one updater process may hold operation.lock at a time. The application waits up to 2 seconds for an in-flight helper to finish. If another process crashed or is still swapping binaries, wait for it to exit. If all peers are closed and an abandoned transaction exists, launching via run-peer-windows.bat or run-peer-linux.sh automatically triggers recovery.
Interrupted update and missing peer-app.jar
If a system crash or power outage interrupts the binary rename during SWITCHING:
  • Both run-peer-windows.bat and run-peer-linux.sh detect a missing peer-app.jar with an existing .p2p-update/ journal and automatically invoke: 
    java -Djava.awt.headless=false -Dfile.encoding=UTF-8 -cp .p2p-update/helper.jar vn.edu.p2p.peer.update.UpdateInstaller --recover .
  • The installer restores the known-working previous.jar into peer-app.jar after verifying its digest, records ROLLED_BACK, and relaunches the original version.
Installation unsupported / running from IDE
Automated self-update requires running from an ordinary writable peer-app.jar on local Windows or Linux storage. When running from an IDE (target/classes) or a read-only volume, update discovery and release notes remain visible, but automated self-installation is disabled with explicit guidance to download the release ZIP manually.
GitHub rate limit exceeded (HTTP 403 / 429)
The client queries GitHub Releases without authentication, subject to GitHub's standard IP limit (60 requests per hour). If exceeded, the Update dialog displays the rate limit reset time (e.g. retry after 120s). The client does not spam or auto-retry; wait until the reset time or download updates directly from the GitHub Releases page.
